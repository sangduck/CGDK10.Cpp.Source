Receive 최적화 net.io.receivable.stream*, net.io.receivable.datagram*, net.io.receivable.stream.h, net.definitions.socket.h

수신 경로에 들어간 최적화 기법을 플랫폼과 단계별로 정리한다. 목표는 세 가지다.

  • 받은 데이터를 앱까지 복사 없이 넘긴다.
  • recv 한 번에 최대한 많이 받는다. 트래픽에 맞춰 버퍼 크기를 바꾼다.
  • 이벤트 하나당 syscall 과 할당을 최소로 한다.

공통 구조 : 받은 버퍼에서 바로 처리

  • 소켓마다 진행 중인 수신은 하나다. 스트림이라 순서를 지키기 위해서다.
  • 수신 버퍼는 풀에서 온 shared_buffer 다. process_packet() 이 그 안에서 메시지를 잘라 on_message 에 버퍼의 조각으로 넘긴다. 앱으로 복사하지 않는다.
  • 앱이 메시지를 쥐고 있어도 안전하다. 조각이 원본 버퍼의 참조를 가진다.
  • 메시지 경계에 걸친 꼬리만 남기고(m_buffer_received) 다음 수신은 그 뒤의 빈 공간에 이어 받는다.
  • 프레이밍 : 오프셋 0 의 크기 필드(헤더 포함 길이)로 자른다. 다음 메시지에 필요한 크기를 돌려주어 버퍼 준비에 쓴다.

수신 버퍼 크기 규칙

IOCP, epoll, io_uring RECV 가 같은 규칙을 쓴다.

상황동작
시작1 KB (DEFAULT_BYTES_TCP_MESSAGE_BUFFER)
창을 다 채워 받음8배로 키운다. 1 KB → 8 KB → 64 KB (MAX_BYTES_RECEIVE_WINDOW_GROWN)
기다리는 메시지가 더 큼그 메시지 크기로 (최대 MAX_TCP_MESSAGE_SIZE)
작은 수신이 연속 64번작은 버퍼로 줄인다 (COUNT_SMALL_RECEIVES_TO_SHRINK)
창을 채운 수신, 큰 수신작은 수신 카운트를 리셋
  • 64 KB 에서 멈추는 이유 : 더 큰 창은 캐시 밖으로 나가 메시지당 CPU 가 는다(64 KB 메시지 기준 +20%).
  • 줄이기에 히스테리시스를 둔 이유 : 도착량이 들쭉날쭉하면 작은 수신 한 번에 줄였다가 다음 폭주에 다시 키우는 요동이 생긴다. 이벤트마다 재할당하고 recv 당 약 700 B 만 받았다.
이 요동(r11345 회귀)은 Linux 에서 같은 데이터에 recv 를 수백 배 부르게 했다. 메시지당 CPU 가 서버 2배·클라이언트 9배로 늘고 큰 묶음 처리량이 약 -22% 였다. r11371 에서 히스테리시스로 고쳤다. Windows IOCP 는 해당 없었다. 이것으로 서버 recv 횟수는 돌아왔지만 메시지당 CPU 는 서버 −17% · 클라이언트 −24% 줄어드는 데 그쳤고, 남은 원인(send cork)은 r11471 에서 고쳤다(큰 묶음 push 처리량).

Windows (IOCP)

  • Overlapped WSARecv 하나를 상시 걸어 둔다(Proactor). 접속과 동시에 prepare_receive().
  • 완료되면 받은 버퍼에서 메시지를 모두 처리한 뒤 다음 WSARecv 를 건다. 완료 0 바이트나 오류는 접속 종료.
  • 수신 버퍼 SO_RCVBUF 를 명시 설정한다(최대 8 MB).
  • loopback 접속은 SIO_LOOPBACK_FAST_PATH 로 지연을 줄인다.
  • Nstream_queue : 받자마자 다음 수신을 다시 걸고 처리는 다른 thread 에서 순서대로 한다. 파일 수신처럼 대량 데이터에 맞다. 처리가 가벼우면 오히려 부담이다.
  • RIO(Registered I/O) 판 Nstream_rio 구현이 있다.

Linux (epoll)

  • IOCP 와 같은 버퍼 방식 : 처리되지 않은 데이터 뒤의 빈 공간에 바로 recv 한다. 이벤트마다 FIONREAD 로 크기를 묻고 새로 할당해 복사하지 않는다.
  • 빈 공간이 모자라면 버퍼를 이 소켓만 쥐고 있고 크기가 충분할 때 남은 데이터를 앞으로 옮긴다(할당 없음). 앱이 메시지를 쥐고 있으면 덮어쓰지 않고 새로 할당해 꼬리만 복사한다.
  • 창을 다 채웠으면 남은 데이터가 더 있을 수 있어 이어서 받는다. 이벤트 하나에 최대 8번(MAX_RECEIVE_PER_EVENT). 덜 채웠으면 끝내고 EPOLLONESHOT 을 재무장한다.
  • send cork : 받은 메시지를 처리하며 같은 소켓에 보내는 응답을 모아 처리 끝에 한 번에 보낸다(send 최적화).
  • 소켓 버퍼는 기본 미설정. 명시 SO_RCVBUF 는 커널 autotuning 을 끈다.
  • TCP_QUICKACK 은 영구가 아니라 recv 마다 다시 건다(socket option 을 켠 경우).
  • acceptor "cpu_affinity" : accept 된 소켓을 SO_INCOMING_CPU 의 CPU 에 고정된 io_context 에 배정한다. NIC 큐와 처리 CPU 가 같아 캐시 지역성이 좋아진다.
  • busy poll : epoll_wait 자체의 busy poll(kernel 6.9+ EPIOCSPARAMS, r11429)과 소켓 SO_BUSY_POLL. 잠들기 전에 NIC 큐를 돌아 지연을 줄인다. loopback·UDS 는 효과가 없다.
  • acceptor "tcp_defer_accept" : 첫 데이터가 올 때까지 accept 를 미룬다. 클라이언트가 먼저 보내는 프로토콜에서 빈 accept 처리를 없앤다.

Linux UDP

  • recvmmsg 로 한 번에 여러 데이터그램을 받는다. 배치 크기는 도착량에 맞춰 1 ~ 32 로 바뀐다.
  • 데이터그램마다 풀 버퍼 하나를 쓴다. 메시지를 복사하지 않는다.
  • r11392 까지 Linux UDP 는 수신 자체가 안 됐다(executable 에 소켓이 연결되지 않음). r11394 에서 고친 뒤 64 B echo 443K msg/s(8 코어) ~ 624K msg/s(32 코어), Release.

Linux (io_uring)

구조와 벤치 전체는 io_uring 백엔드 문서에 있다. 수신에 해당하는 것만 적는다.

readiness 모드 (CGDK_IO_URING=1)

  • epoll 과 같은 준비 이벤트 모델(POLL_ADD)이라 수신 코드는 epoll 과 같다.
  • worker 가 처리 중 낸 재무장 요청은 다음 enter 한 번으로 묶어 제출한다. epoll 은 이벤트마다 epoll_ctl 이다.

completion 모드 (CGDK_IO_URING=completion) — 단계별로 들어갔다.

단계기법효과·이유
2단계 (r11441)소켓당 RECV op 하나 상시. 버퍼 규칙은 epoll 재사용recv syscall 이 없다. 완료 통지가 곧 데이터
3단계 (r11453)multishot RECV + provided buffer ring (ring 당 16 KB x 256)op 한 번에 도착마다 CQE. 재제출 비용 없음. 작은 메시지에서 같거나 빠름
4단계 (r11457)provided buffer 를 그 자리에서 처리(무복사). 마지막 참조가 사라질 때 ring 에 반납IOCP 처럼 받은 버퍼가 곧 메시지. UDS 64 B +6%
모드 전환 (r11459)큰 트래픽은 가변 버퍼 RECV, 작은 메시지는 multishot16 KB 고정 버퍼에 큰 메시지가 조각나던 문제 해결
  • -ENOBUFS : provided buffer 가 바닥나면 RECV 하나를 자기 버퍼로 내고 그 완료 뒤 다시 multishot. 커널은 recv 전에 버퍼를 고르므로 기다리는 데이터 없이도 온다.
  • 무복사 수신 : 남은 데이터가 없으면 provided buffer 를 shared_buffer 의 source 로 감싸 그대로 처리한다. 앱이 메시지를 쥐면 그동안 반납되지 않는다. 경계에 걸친 꼬리만 복사.
  • 모드 전환 : 한 완료가 provided buffer 를 다 채웠거나 그보다 큰 메시지를 기다리면 RECV 모드로 바꾼다. RECV 모드에서 작은 수신이 16번 이어지면 multishot 으로 돌아간다. 새 접속은 multishot 으로 시작한다.
  • 실행 순서 : multishot 은 op 하나에 CQE 가 여럿이다. 한 ring 의 CQE 는 한 번에 한 thread 에서 CQ 순서대로 실행되게 했다.
  • A/B 스위치 : CGDK_IO_URING_MULTISHOT=0, CGDK_IO_URING_ZC_RECV=0, CGDK_IO_URING_RECV_ADAPTIVE=0.

UDS

  • 수신 코드는 TCP 와 같다. 위의 모든 기법이 그대로 적용된다.
  • 커널 TCP 스택을 거치지 않아 저부하 지연 p50 이 16.7 → 9.3 µs. 자세한 것은 UDS 문서.
  • TCP_QUICKACK, busy poll 은 적용되지 않는다.

  • 32 코어 8 thread : completion 기본값이 모든 케이스에서 epoll 보다 빠르다. tcp 64 B +26%, UDS +63%, 16 B x256 +37%, 64 KB +12%, UDP +43%. 16 thread 에서는 epoll 이 오히려 떨어지고(추정 : 공유 epoll fd 경합) completion 은 늘어 +55 ~ +172% 다.
  • 메시지당 CPU (8 thread, epoll / 기본값) : tcp 64 B 0.65 / 0.50 µs, UDS 0.53 / 0.31 µs, 16 B x256 8.9 / 6.3 µs. 모든 thread 가 100% 라 처리량은 메시지당 CPU 로 정해진다. completion 은 recv · epoll_wait · epoll_ctl 이 없다.
  • tcp 64 B 의 옛 열세(epoll 의 −23 ~ −37%)는 수신이 아니라 송신 쪽이었다 : multishot 은 도착마다 CQE 를 따로 내고 CQE 마다 send cork 가 끝나, 창 16 개가 세그먼트 2 ~ 3 개로 갈라진 채 다시 합쳐지지 않았다(데이터 세그먼트 메시지당 0.25 대 epoll 0.125). 배치 send defer(r11497)가 CQE 배치 끝에 socket 마다 한 번 보내 0.125 로 돌아왔다. UDS 는 send 가 싸서 그때도 epoll 보다 빨랐다.
  • multishot 의 효과 : 8 thread 에서 단일 RECV 보다 tcp 64 B +47%, UDS +46%, 16 B x256 +10%. 소켓마다 RECV 를 다시 내던 비용이 사라진다.
  • 수신 모드 전환의 효과 : 64 KB 에서 multishot 고정보다 8 thread +42%, 4 thread +29%. 큰 메시지를 가변 버퍼 RECV 로 한 번에 받는다. 작은 메시지 케이스는 노이즈 안이다.
  • 64 KB 4 thread 는 epoll 이 두 배다 : 접속이 4 개라 completion 은 ring 4 개(thread 4 개)에서만 돌고, 16 KB 이상 단일 버퍼를 보내는 SEND_ZC 가 loopback 에서는 손해다(받는 쪽이 어차피 복사). zerocopy 를 끄면 completion 64 KB 가 4 thread +28%, 8 thread +16% 오른다. 실 NIC 에서는 다를 수 있어 기본값은 두었다.
  • completion 의 이득은 thread 가 많을수록 커진다(thread 마다 ring). 같은 장비에서도 회차 범위가 넓으니(64 KB 는 같은 구성 157 K ~ 221 K) 구성끼리 몇 % 차이는 같다고 본다.
