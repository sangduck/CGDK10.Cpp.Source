executor post · runnext Linux · handler 안에서 자기 executor 로 post · r11560 (epoll) · r11565 (io_uring) · r11569 · r11571 (scheduler)

worker 가 handler 안에서 자기 executor 로 다음 일을 post 하는 경로(coroutine 재개, stream_queue · messageable.queue 수신, executable batch)를 쟀다. 구현은 Executor system 의 executor::io_context 다.

요약
  • runnext 슬롯(epoll r11560, io_uring 두 백엔드 r11565) : worker 가 실행 중 자기 executor 로 post 하면 thread 의 슬롯에 넣고 묶음 끝에 바로 실행한다. 사슬 1개 0.50M → 13.3M hops/s(27배), worker 8개 · 사슬 32개 3.1M → 94M(31배).
  • 외부 thread 의 post 처리량과 쉬던 executor 깨우기 지연은 그대로다.
  • 순서 : 새 post 가 슬롯을 차지하고 이전 것은 공유 큐로 간다(Go 의 runnext 와 같음). worker 1개 executor 에서도 연달아 post 한 순서가 바뀔 수 있다. CGDK_RUNNEXT=0 으로 끈다.
  • 기본 백엔드(io_uring completion, r11556) : 사슬 1개 1.37M → 12.1M(9배), 8개 1.57M → 49.9M(32배), 32개 2.09M → 76.6M(37배).
  • scheduler post_at 깨우기 줄이기(r11569) : 자는 thread 를 더 이른 것이 올 때만 lock 밖에서 깨운다. post_at 처리량 Windows 1.4 ~ 1.9배, Linux 미래 시각 최대 3배(3.0M → 9.2M/s). 아래.
  • scheduler cancel 인덱스 힙(r11571) : cancel 이 선형 탐색에서 O(log n) 으로, 대기 10만에서 Linux 3.1 µs → 36 ns, Windows 4.7 µs → 54 ns. thread 4개 동시 post_at 은 10 ~ 15% 낮다. 아래.

동작

  • 전 : post 는 mutex 큐에 넣고 큐가 비었다 찰 때 eventfd 를 쓴다. post 한 worker 는 아직 실행 중이라 eventfd 가 자던 다른 worker 를 깨우고 일이 그쪽으로 옮겨 간다. 한 걸음에 context switch 약 2회, 약 2 µs.
  • 후 : 묶음을 실행하는 동안 같은 thread 의 같은 executor 로의 post 는 thread_local 슬롯 1개로 간다(lock · eventfd · 깨우기 없음). 슬롯이 차 있으면 이전 것을 공유 큐로 보내고 새 것을 넣는다.
  • 슬롯은 묶음 직후, 다음 epoll_wait / io_uring_enter 전에 실행한다. 실행 중의 post 는 다시 슬롯으로 가서 사슬이 같은 thread 에서 이어진다.
  • 20 µs 가 지나면 남은 것을 공유 큐로 보낸다. 긴 사슬이 그 worker 의 socket event 를 오래 막지 않는다. worker 가 잠들 때 슬롯은 항상 비어 있다.
  • handler 안에서 executor 를 다시 돌리면 바깥 슬롯을 보관했다가 되돌린다.
  • io_uring completion : 슬롯 항목도 묶음처럼 ring 에 게시한다. 오래 도는 항목은 다른 worker 가 ring 을 빌려 가고, 시작할 때 ring 이 빌려 간 상태면 그 항목 뒤 나머지는 공유 큐로 보낸다. io_uring readiness : 슬롯 항목이 남긴 re-arm 을 끝에 한 번에 제출한다.

측정 구성

  • 장비 : i9-13900K(P 8코어 × 2 + E 16코어 = 32 thread), Ubuntu 26.04.1, kernel 7.0, g++ 15.2 Release(-O3). thread 고정 없음. 하이브리드 CPU 라 thread 가 걸린 코어에 따라 흔들려 교대 5회의 최소 ~ 최대와 중앙값을 적는다.
  • A 외부 post : worker 가 아닌 thread P 개가 빈 executable 을 post.
  • B 자기 post 사슬 : executable K 개가 실행될 때마다 자기 자신을 같은 executor 에 다시 post. 사슬 1개 = 한 걸음의 지연, 여러 개 = 처리량.
  • C 깨우기 지연 : 300 µs 쉬게 한 뒤 외부에서 post 해 실행까지 걸린 시간, 2,000회.
  • 전 / 후는 같은 바이너리에서 CGDK_RUNNEXT=0 / 1 로 바꿨다(2026-10-24, r11560).

scheduler post_at · 깨우기 줄이기 (r11569)

executor::scheduler 는 post_at(시각 지정 1회 실행)을 우선순위 큐(binary heap, mutex)에 넣고 전용 thread 가 시각이 되면 다른 executor 로 넘긴다. system_executor::post(exec, time), schedulable, coroutine 재개, strand post_at 이 이 경로를 쓴다.

  • 전 : 넣은 것이 가장 이른 것이 될 때마다 lock 안에서 깨웠다(condition_variable notify, Windows 는 SetEvent 도). post_at(object_ptr&&) 은 raw 포인터를 거쳐 AddRef · Release 를 한 번 더 했다.
  • 후 (r11569) : scheduler thread 는 잠들기 전에 lock 안에서 "자는 중"과 스스로 깨는 시각을 기록한다. post_at 은 자는 중이고 그 시각보다 이를 때만 lock 밖에서 깨우고, 그 시각을 낮춰 뒤이은 늦은 것이 다시 깨우지 않게 한다. object_ptr 은 이동만 한다.
  • 측정 : 별도 scheduler 하나, worker 1개 executor, thread T 개가 2초 동안 post_at(now + [0, D)). Windows = DOLPUNG Core Ultra 7 270K Plus(24 thread), Linux = POKPUNG i9-13900K(32 thread, Ubuntu 26.04.1, kernel 7.0, g++ 15.2), 둘 다 Release. 전 / 후 교대 2회.

scheduler cancel · 인덱스 힙 (r11571)

cancel(Iexecutable*) 은 힙 전체를 선형 탐색했다(lock 보유). 인덱스 힙을 적용했다(r11571, r11569 위). 지연 취소는 구현 · 측정만 하고 적용하지 않았다.

  • 인덱스 힙 (적용) : executable(Iexecutable::m_scheduler_position, 8 B)이 힙 위치를 기억하고 항목이 옮겨질 때마다 위치를 쓴다. cancel O(log n). 같은 executable 을 겹쳐 걸면 그동안만 선형 탐색으로 대체한다.
  • 지연 취소 (적용 안 함) : 항목에 넣을 때의 세대를 두고 cancel 은 executable 의 세대만 올린다(O(1)). 버린 것은 가장 이른 것이 될 때 버리고, 절반을 넘으면 힙을 다시 만든다. 같은 executable 의 대기가 한 번에 모두 취소되고, 취소한 객체의 해제가 늦어진다.
