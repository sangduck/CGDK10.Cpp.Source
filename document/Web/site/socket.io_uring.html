io_uring 백엔드 · Linux 벤치 system/object/api.io_context.uring.{h,cpp}, executor.Iio_context.h, net.socket (Linux)

Socket system 의 하위 문서. Linux 에서 epoll 대신 쓸 수 있는 io_uring 백엔드의 구조, 만들면서 만난 문제, 그리고 실 장비에서 epoll 과 비교한 벤치마크를 정리한다(r11393~r11446, 2026-10-22~23). 결론부터 : 기본은 epoll. 준비(readiness) 모드는 thread 가 늘수록 뒤처지고, 완료(completion) 모드는 서버도 같은 backend 로 잰 공정 벤치(배치 send defer r11497 이후)에서 8 · 16 thread 의 모든 케이스가 epoll 보다 빠르다(아래 "5단계" 와 "4 · 8 · 16 thread" 절). 그 앞의 표들은 벤치의 서버 socket 이 epoll 에서 돈 측정이라 클라이언트 쪽만 그 backend 였다.

켜는 법

  • executor::set_default_io_backend(executor::io_backend::io_uring) 또는 환경변수 CGDK_IO_URING=1(true/on/uring). io_context 가 만들어지는 시점에 읽으므로 system_executor 초기화나 make_io_context_threads() 전에 정해야 한다. default_io_backend(), is_io_uring_available()(커널이 io_uring 을 지원하는가).
  • api::io_context_linux(platform.h 의 api::io_context)가 create() 때 epoll(io_context_epoll_direct) 또는 io_uring(io_context_uring) 객체를 만든다. io_uring 이 불가(커널 5.13 미만, io_uring_disabled)면 경고 로그 후 epoll 로 fallback. executor::Iio_context::backend() 가 실제 백엔드를 돌려준다(MSG_ZEROCOPY 가 io_uring 일 때만 켜지는 데 쓴다).
  • Windows 는 항상 IOCP. 소켓 코드(*.epoll.cpp)는 두 백엔드에서 그대로 돌아간다.

구조

항목내용
인터페이스io_context_epoll_direct 와 같다 : attach / detach / modify / pop_events / post_executable / get_result. 소켓마다 IORING_OP_POLL_ADD 를 걸고 CQE 를 epoll_event 로 바꿔 돌려주는 준비 이벤트 모델. IORING_OP_RECV/SEND 는 쓰지 않는다.
syscallliburing 없이 io_uring_setup / io_uring_enter 직접 호출과 SQ·CQ·SQE 배열 mmap. SQ 4096, CQ 4배. IORING_FEAT_EXT_ARG(timeout 대기), NODROP, SINGLE_MMAP. is_available() 은 io_uring_setup(8) 프로브.
등록 관리api::io_context_Nepoll 의 레지스트리(handle → executable, generation, 이벤트 마스크)를 공유. user_data = handle | generation<<32 로 닫힌 fd 가 재사용된 뒤 오는 stale CQE 를 걸러낸다.
poll 모델모든 poll 은 1회성. EPOLLONESHOT 등록(TCP)은 소켓 코드의 set_event → modify() 가 재무장한다 : poll 이 살아 있으면(m_armed[handle]) POLL_REMOVE + POLL_ADD, 끝났으면 POLL_ADD. EPOLLONESHOT 없는 등록(UDP 의 EPOLLET, listen, post eventfd)은 그 CQE 를 꺼낸 thread 가 이벤트 처리를 끝낸 뒤 flush_pending() 에서 같은 마스크로 다시 POLL_ADD 한다(thread_local 목록). EPOLLET 과 같은 동작 : 처리 중 도착한 것은 drain 으로 소비되고 이후 도착이 CQE 하나를 만든다.
제출 묶기worker thread(pop_events 를 지난 thread)는 처리 중 쓴 SQE 를 바로 제출하지 않고 flush_pending()(executor::io_context 가 배치 처리 뒤 호출) 또는 다음 pop_events() 에서 io_uring_enter 한 번으로 제출한다. worker 가 아닌 thread 는 즉시 제출.
CQ 대기한 thread 만 커널에서 대기(lockable_cq, std::timed_mutex)하고 나머지는 자기 대기 시간만큼만 lock 을 기다린다. 못 잡으면 빈손으로 돌아오고 이벤트는 커널에 있는 thread 가 처리한다. 음수 res 는 EPOLLERR|EPOLLHUP, 취소·nop CQE(TAG_IGNORE)와 -ECANCELED 는 버린다.
posteventfd + 큐(executable_post). eventfd 도 소켓처럼 poll 한다.
수명RING_GUARD 가 ring 사용 thread 수를 세고, destroy() 는 handle 무효화 → nop 으로 대기자 깨움 → 사용자 0 까지 대기 → 등록 해제 → munmap. 디스패처는 destroy 뒤에도 백엔드 객체를 들고 있다(정지 중 소켓 close 가 set_event 를 부른다).

설계 경위 — 세 번 바꾼 이유

처음 설계에서 지금 형태까지 세 가지 문제를 겪었다. 각각이 테스트 수치로 드러났고, 모두 "epoll 의 공유 fd + 다중 thread 모델을 io_uring 에 억지로 맞춘" 데서 나온 비용이다.

  1. multishot poll 의 CQE 폭주. EPOLLONESHOT 없는 등록을 IORING_POLL_ADD_MULTI 로 두었더니 깨어날 때마다 CQE 가 하나씩 쌓였다(epoll 처럼 합쳐지지 않음). UDP echo 가 epoll 의 1/13(50K vs 640K msg/s). 또 커널 6.6 은 IORING_POLL_UPDATE_EVENTS 를 multishot 과 함께 받으면 EINVAL 을 돌려줘 재무장이 조용히 사라졌다. → 모든 poll 을 1회성으로.
  2. 재무장 시점. CQE 를 꺼낼 때 바로 재무장 SQE 를 썼더니, SQ 는 공유라 다른 thread 의 submit 에 끌려 들어가 아직 drain 중인 소켓의 poll 이 즉시 다시 완료되고 두 thread 가 같은 UDP 소켓을 동시에 처리했다(데이터그램 유실 923/1000, post eventfd 정지). → 재무장은 그 thread 가 이벤트 처리를 끝낸 뒤 flush_pending() 에서.
  3. CQ lock 굶주림. 커널에서 대기하는 thread 가 plain mutex 를 1초(executor 의 대기) 동안 잡고 있어, wait_complete_connecting / wait_complete_closed 처럼 2 ms 로 executor 를 펌핑하는 thread 가 worker 들과 mutex 를 경쟁하며 수 초씩 굶었다. 접속 직후 stop() 200회 테스트가 1.4초~250초로 흔들렸다. → timed_mutex, 호출자의 대기 시간만큼만.
진단 방법 : strace -f 를 붙이면 ptrace 정지가 thread 순서를 바꿔 이런 지연 버그가 사라진다. gdb 스냅샷(thread apply all bt, ring 의 *cq_head / *cq_tail 읽기)으로 CQE 가 쌓여 있는지·없는지를 보는 쪽이 맞았다. linux_io.io_uring_executor 테스트의 소요 시간(정상 1.4초)이 지연 버그의 지표다.

함께 드러난 소켓 계층 버그

  • 접속 중 close 경쟁(r11395~r11397): 다른 thread 가 접속 완료(EPOLLOUT)를 처리하는 중 또는 막 끝낸 뒤에 SYN 소켓을 닫으면 아무도 disconnect 를 끝내지 않아 wait_complete_closed() 가 30초 timeout 까지 기다렸다. epoll 에서도 이론상 같은 경쟁이지만 io_uring 은 접속 완료 CQE 가 수 us 안에 와서 매번 드러났다. process_complete_connecting() 의 가드가 세 경우(미시작 / 처리 중 → EPOLLHUP 큐 / 완료 후 → 즉시 disconnect)를 모두 처리한다.
  • Linux UDP 수신 불가(r11394): receivable::Ndatagram::prepare_receive() 가 executable_socket 에 socket 을 연결하지 않아 EPOLLIN 이 와도 처리 함수가 불리지 않았다. r11392 이전 Linux 에서 Nudp 는 한 번도 수신하지 못했다(벤치 표의 0).
  • 풀 재사용 socket 의 옛 socket_option(r11400): acceptor 가 옵션을 주지 않으면 "socket 자신의 값" 을 유지하는데, 풀에서 재사용된 socket 은 직전 acceptor 의 값을 그대로 가지고 있었다. 할당 직후 기본값으로 되돌린다.

completion 모드 (CGDK_IO_URING=completion)

api::io_context_uring_cq(r11437~r11448) 는 IOCP 와 같은 완료 모델이다. worker thread 마다 ring 하나를 두고(CQ 락 없음), 소켓은 RECV / SENDMSG / ACCEPT(multishot) / CONNECT op 를 제출해 완료를 process_execute(res, flags) 로 받는다(net.io.receivable.stream.uring.cpp, net.io.sendable.tcp_async_gather.uring.cpp, net.io.connective.acceptor_tcp.uring.cpp). 큰 단일 버퍼는 SEND_ZC. 커널 6.0+ 필요(executor::is_io_uring_completion_available()).

  • 요청은 제출한 thread 의 소유이고 그 thread 가 끝나면 커널이 취소한다. 그래서 poll 과 op 는 어느 thread 가 쓰든 ring 의 staging 에 두고 ring 소유 worker 만 자기 io_uring_enter 로 제출한다(r11444). io_context_threads 의 임시 extra thread 는 ring 을 갖지 않는다(r11448).
  • fd 별 테이블은 hard RLIMIT_NOFILE 크기다. soft(1024)로 잡았을 때 fd 1024 이상의 op 제출이 실패해 접속 2000개 테스트가 절반 실패했다(r11448).
  • acceptor 정지 때 multishot ACCEPT 는 IORING_REGISTER_SYNC_CANCEL 로 커널 쪽 취소를 기다린다. op 가 listen 소켓 파일을 잡고 있어 비동기 취소로는 close() 직후에도 UDS 이름이 남았다(r11448). 정지 직후 UDS 리스너가 남는 간헐 실패가 아직 3회 중 1회 있다.

4단계 : 무복사 수신과 소유 worker 의 송신 op (r11457)

  • 무복사 수신(기본 on, CGDK_IO_URING_ZC_RECV=0 으로 끔) : IOCP 가 받은 버퍼를 그 자리에서 처리하듯, 소켓에 남은 데이터가 없으면 provided buffer 를 그 자리에서 process_packet 한다. 버퍼는 풀링되는 Imemory 로 감싸 메시지(shared_buffer 조각)의 source 가 되고, 마지막 참조가 사라질 때 ring 에 반납된다. 메시지 경계에 걸친 꼬리만 복사한다.
  • 소유 worker 의 송신 op(기본 off, CGDK_IO_URING_SEND_OP=1) : 송신 알고리즘(보내는 주체가 있으면 큐잉만, 없으면 바로 보내고 큐를 비울 때까지 gather)은 그대로이고, socket 의 ring 을 소유한 worker 의 "바로 보내기"를 직접 send() 대신 SENDMSG op 로 바꾼다(배치 뒤 enter 에 함께 제출, send syscall 없음).

측정 방법 수정 : 위 표들의 서버는 epoll 이었다 (r11487, r11489)

  • r11487 이전 bench_linux_io.cpp 의 서버 socket 은 case 의 executor 가 아니라 system executor(기본 epoll, 2 x 코어 + 2 thread)에서 돌았다. Linux acceptor 가 accept 한 socket 에 acceptor 의 io_context 대신 system executor 를 줬기 때문이다(r11489 에서 Windows 와 같게 수정 : hook → acceptor 의 io_context → system executor). 그래서 위 3·4단계 표의 "completion" 은 클라이언트만 completion 이었다.
  • 서버까지 completion 에 올리자 accept 된 socket 이 모두 listen socket 의 ring(thread 하나)에 묶이는 문제가 드러났다 : 첫 RECV 를 제출한 worker 의 ring 에 묶이는데 그게 accept 를 실행한 listen ring owner 였다. r11487 이 accept CQE 에서 그 fd 를 round robin ring 에 바인딩한다(tcp 64B x32 completion 2.48M → 10.58M, mistral).
  • 이후 벤치는 서버·클라이언트 모두 case 의 executor 에서 돈다. 이 절 아래 수치만 completion 대 epoll 의 공정한 비교다.

5단계 : 송신 경로 — CQE 배치 끝 송신, buffered 의 SEND op (r11494, r11497)

  • 남은 격차의 원인은 송신이었다. 공정한 벤치에서도 tcp 64B x32 window 16 은 epoll 의 −37%. strace -c -f 로 세면 epoll 은 recv 한 번이 창(16개)을 받아 송신 1회에 메시지 ~6.6개(sendto 0.15/msg), completion 은 multishot RECV 가 도착(세그먼트)마다 CQE 를 하나씩 내고 handler 의 send cork 가 CQE 하나로 끝나 sendto 0.76/msg. 수신 syscall 을 없앤 대신 송신 syscall 이 5배였다.
  • 배치 send defer(r11497, 기본 on, CGDK_IO_URING_BATCH_DEFER=0 으로 끔) : completion executor 가 CQE 배치(최대 32, 실행 10 µs 에 맞춰 적응) 전체를 send_defer 배치로 묶는다(send_defer::begin_batch() / end_batch()). 배치 안의 송신은 그룹 락 안처럼 모였다가 배치 끝에 socket 마다 한 번 나간다.
    • 의미는 그대로 : 배치 안에서도 send cork 의 200 µs 나이 상한이 선다(is_cork_age_checked()), 배치 안의 그룹 락은 풀릴 때 자기 송신을 보낸다, close 직전의 flush(process_flush_deferred_send_on_close)와 scoped_thread_block 의 flush 도 그대로.
    • 배치가 100 µs 넘게 돌면 다음 CQE 전에 모은 것을 보낸다 : 긴 handler 가 같은 배치의 다른 socket 송신을 붙잡는 상한. 이미 읽는 실행 시작 시각을 써서 clock 호출이 늘지 않는다.
    • CQE 하나짜리 배치는 기존 socket cork 그대로. epoll · readiness 경로는 바뀌지 않는다. 배치 안에서는 실행기 auto 묶기(send_defer::auto_scope, r11496)보다 배치가 넓게 묶는다.
  • buffered 도 completion(r11494) : Ntcp_async_gather_buffered(tcp_buffered<>, tcp_queue, redis querier session)는 completion 을 지원하지 않아 completion executor 위에서도 readiness(POLL_ADD)로 돌았다. 이제 gather 와 같이 직접 send + socket 버퍼가 차면 SENDMSG op(큐 앞 묶음, IOV_MAX 개까지), 큰 사용자 버퍼는 SEND_ZC op. op 로 옮긴 묶음은 송신 큐 한도에 세지 않는다(epoll 의 EPOLLOUT 대기분, Windows 의 WSASend 진행분과 같음). 같은 커밋에 gather op 완료가 대기 바이트를 되돌리지 않던 버그(sending_queued_bytes_now() 가 옛 값) 수정.
  • 소유 worker 송신 op(CGDK_IO_URING_SEND_OP=1)는 배치 send defer 와 같이 써도 손해라(tcp 64B 16.25M vs 17.29M, UDS 22.0M vs 29.4M) 기본 off 그대로. 켜면 아직 제출되지 않은 송신 op 를 같은 handler 의 graceful close 가 취소해 데이터를 잃을 수 있다(알려진 문제).

결론과 남은 일

  • 기본은 epoll. readiness io_uring(CGDK_IO_URING=1)은 공유 ring 에 CQ 대기자 하나라는 구조가 thread 수에 비례해 손해라 쓸 이유가 없다.
  • completion 모드(CGDK_IO_URING=completion, thread 당 ring)는 accept socket 분산(r11487)과 배치 send defer(r11497) 이후 32 코어 공정 벤치에서 tcp 64B x32 +14%, UDS +78%, 16B x256 +48%, UDP +43% 로 epoll 을 넘는다(64KB 는 비슷). 남은 조건 : handler 는 짧게(한 ring 의 socket 은 owner thread 하나가 차례로 실행, 블로킹은 r11481 로 다른 worker 가 대신), 8 코어 장비·실 NIC 재측정. thread 수별로는 4 thread +7 ~ +16%(64KB 만 epoll 이 두 배), 16 thread +55 ~ +172%("4 · 8 · 16 thread" 절). 기본값은 아직 epoll 이다.
  • MSG_ZEROCOPY(sendable::Itcp_gather, 16KB 이상 단일 버퍼)는 io_uring 백엔드에서만 켜진다. epoll 에서는 통지 1건당 epoll_wait/epoll_ctl 이 더 들어 손해. loopback 에서는 completion 의 SEND_ZC 도 손해다(받는 쪽이 복사 : 64KB 를 복사로 보내면 +16 ~ +28%) : 실 NIC 에서 잴 것.
  • acceptor cpu_affinity(SO_INCOMING_CPU 의 CPU 에 고정된 io_context 에 accept 소켓 배정)는 loopback 에서 측정할 수 없다(모두 같은 CPU). 실 NIC 의 RSS 큐 환경에서 재야 한다.
