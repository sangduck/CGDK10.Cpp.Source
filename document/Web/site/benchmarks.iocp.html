Windows IOCP 송신 락 밖 WSASend (r11530) · 실행기 자동 묶기 (r11531) · r11529 대비

Windows IOCP 송신 경로를 두 군데 고치고, 고치기 전 r11529 와 비교했다. 하나는 tcp<> · tcp_buffered<> 의 WSASend 를 송신 큐 락 밖으로 뺀 것이다(r11530). 다른 하나는 Linux 처럼 실행기가 executable 마다 send_defer::auto_scope 를 여는 것이다(r11531, 기본 켜짐). 함께 검토한 FILE_SKIP_COMPLETION_PORT_ON_SUCCESS 는 효과 상한만 재고 미뤘다(아래).

요약
  • echo 파이프라인(32 연결 × 16 개, 64 B) : 238만 → 754만 msg/s (× 3.2), 메시지당 CPU 3.27 → 1.04 µs. auto_scope 덕분이다. 전에는 받은 메시지마다 WSASend 1번과 IOCP 완료 1번이 들었고, 이제는 수신 한 번에 대한 응답이 WSASend 한 번으로 나간다.
  • 여러 thread → socket 1개(fan-in) : 404만 → 1,054만 msg/s (× 2.6), 회차 범위 996만 ~ 1,493만. 락 밖 WSASend 덕분이다. 전에는 보내는 thread 들이 다른 thread 의 WSASend 가 끝나기를 락에서 기다리며 잠들었다.
  • 여러 thread → socket 32개(fan-out) : 69만 → 1,715만 msg/s (× 25), 메시지당 CPU 16.6 → 0.89 µs.
  • ping-pong · 64 KB · UDP : 모을 것도, 다툴 것도 없어 변화가 없다(회차 범위 안).

측정 구성

  • 장비 : Windows 11 Pro, Intel Core Ultra 7 270K Plus(24 코어), loopback. VS 18 x64 Release.
  • 소스 : r11529 를 체크아웃해 세 판을 빌드했다. 기준(r11529), auto_scope 만, auto_scope + 락 밖 WSASend(= r11531). 판마다 벤치 바이너리가 따로다(라이브러리 정적 링크).
  • 벤치 : benchmark/3.socket_iocp_send/bench_windows_io.cpp. 케이스마다 실행기를 따로 만든다(make_io_context_threads, 8 thread). 서버 socket 도 그 실행기에서 돈다. echo 는 클라이언트마다 window 개를 띄워 두고 받으면 다시 보낸다. fan-in · fan-out 은 실행기 밖 std::thread 8 개가 64 B 를 큐가 64 KB 아래일 때 계속 보낸다.
  • 값 : 클라이언트가 받은 메시지/초. µs/msg 는 측정 구간의 프로세스 CPU 시간 ÷ 메시지. 세 판을 번갈아 5라운드 × 3초 돌린 중앙값이다. fan 케이스는 보낸 수와 받은 수가 같은지도 확인했다.

1. 락 밖 WSASend (r11530)

Ntcp_async_gather(tcp<>) 와 Ntcp_async_gather_buffered(tcp_buffered<>) 의 Windows 경로다.

  • 전 : 보내는 thread(m_flag_sending) 가 송신 큐 락 m_lockable_sending(recursive_mutex) 을 잡은 채 WSASend 를 불렀다. 그동안 같은 socket 에 보내는 다른 thread 는 큐에 넣기만 하면 되는데도 그 syscall 이 끝날 때까지 락에서 잠들었다. fan-in 에서는 CPU 를 4 코어만 썼다. fan-out 에서는 송신 하나마다 WSASend 1번(메시지 1개)이 나갔다.
  • 후 : 큐 조작만 락 안에서 한다(m_queue_pending 에 넣기, m_queue_sending 으로 가져오기). 보내는 thread 는 락을 놓고 WSASend 한다. 그 사이 다른 thread 는 기다리지 않고 m_queue_pending 에 쌓는다. 그래서 다음 WSASend 가 더 많이 묶는다. 보내는 thread 는 언제나 하나라 순서와 중복 송신 보장은 그대로다.
  • close 와의 경합 : handle 을 읽고 WSASend · shutdown 하는 것은 새 락 m_lockable_send_call 안에서 한다. close 도 그 락 안에서 handle 을 INVALID 로 바꾼다. 그래서 닫힌 뒤 같은 값으로 다시 만들어진 다른 socket 에 보내지 않는다. 완료가 WSASend 가 돌아오기 전에 다른 thread 에 올 수 있어, m_queue_sending 을 지우는 것도 그 락 안에서 한다. 락 순서는 송신 큐 락 → send call 락 한 방향뿐이다.
  • 그대로인 것 : Ntcp_async(tcp_no_gather) 는 여러 thread 가 동시에 WSASend 하므로 락 안에서 불러야 순서가 지켜진다. raw · crypt · sync sendable 과 Linux 도 바꾸지 않았다.
  • 헤더 멤버가 늘었다(net.io.sendable.tcp_async_gather.h, _buffered.h). CGDK lib 전체와 사용하는 쪽을 다시 빌드해야 한다.

2. 실행기 자동 묶기 (r11531)

Linux 에서 r11496 부터 하던 것을 Windows 실행기에도 넣었다. 기본 켜짐이다. 규칙은 send cork · 서버 push 의 "자동 묶기" 와 같다.

  • 실행기(executor::io_context) 가 executable 하나를 실행할 때마다 send_defer::auto_scope 를 연다. 같은 socket 으로 이어지는 송신은 executable 이 끝나거나 다른 socket 으로 보낼 때 WSASend 한 번으로 나간다.
  • close, scoped_thread_block, 큐 한도, send_defer::flush() 에서는 그 전에 보낸다. 끄려면 send_defer::enable_auto(false) 를 쓴다.
  • 주의 : handler 가 요청을 보낸 뒤 scoped_thread_block 없이 그 응답을 기다리면, 요청이 아직 모여 있어 교착될 수 있다. 그런 곳은 send_defer::flush() 를 먼저 부른다.
  • .cpp 만 바뀌었다(executor.io_context.cpp). 다시 링크하면 된다.

3. FILE_SKIP_COMPLETION_PORT_ON_SUCCESS : 미룸

즉시 완료된 I/O 의 IOCP 왕복을 없애는 옵션이다. 순수 Win32 loopback echo(같은 장비, 8 thread, 5라운드)로 효과의 상한만 쟀다.

  • 작은 메시지의 이득은 송신 완료 IOCP 패킷 하나만큼이다. CGDK 의 메시지당 비용은 순수 Win32 의 2 ~ 6 배라 실제 비율은 이보다 작다.
  • 큰 이득(64 KB)은 수신을 그 자리에서 처리해야 나온다. 그러려면 수신 · 송신 · accept · connect · disconnect(TF_REUSE_SOCKET 으로 handle 재사용) · UDP 의 모든 경로가 동기 성공을 처리해야 한다. 그래서 따로 설계하기로 했다.

검증

  • Windows VS18 x64 Debug · Release : net_socket.http 93, system.object execute 65, server_system.service 172 (skip 6) · 176 (skip 2) 통과.
  • test_send_defer_auto.cpp 를 Windows 에서도 빌드한다(전에는 Linux 만). 자동 묶기 켬 · 끔 × gather · buffered 에서 소켓 섞어 보내기, tick 묶음, 1 개씩, 보내고 closesocket, 예외, 다른 thread 와 동시 송신을 시험한다.
  • 새 테스트 send_defer_auto.close_while_sending_{gather,buffered} : thread 4 개가 보내는 중에 closesocket 하기를 60 회 반복한다. 도착한 것은 sender 마다 순서대로여야 하고, close 직후 accept 된 socket 은 아무것도 받지 않아야 한다.
