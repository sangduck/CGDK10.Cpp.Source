send cork · 서버 push Linux epoll · echo 와 tick push · 원본 r11340 대비 HEAD r11478 · 자동 묶기 r11496

epoll 송신을 묶어 보내는 두 장치를 원본(r11340, epoll 최적화 전)과 비교했다. send cork 는 수신 처리 중 같은 소켓에 보내는 응답을 모은다(자동). send_defer::scope 는 수신 handler 밖, 예를 들어 tick 스레드의 송신을 모은다(호출하는 쪽이 범위를 연다). 알고리즘은 send 최적화 에 있다.

요약
  • echo 파이프라인(64 연결 × 16 개) : HEAD 에서 cork 를 켜면 2,435만 ~ 2,559만 msg/s, 0.31 ~ 0.33 µs/msg. 끄면 270만 ~ 299만, 원본 buffered 는 1,013만 · 0.79 µs. syscall 은 메시지당 0.25(끄면 1.19).
  • ping-pong · 64 KB : 모을 것이 없어 cork 를 켜도 꺼도 같다. 원본 대비 ping-pong 처리량 +24 ~ 27 %, CPU −20 % 는 수신 경로 개선에서 온다.
  • handler 가 send 뒤에 일할 때 : 네 시나리오 모두 cork 켬이 처리량 · p50 · p99 가 가장 좋다. 200 µs 상한(r11471) 의 손해는 보이지 않았다.
  • tick push(handler 밖) : cork 대상이 아니다. r11478 까지는 scope 없이 보내면 소켓당 16 개 이상에서 원본 buffered 보다 CPU 1.7 ~ 4.5 배, 410만/s 요청에 55 % 만 전달했다. 소켓별 send_defer::scope 면 원본보다도 CPU 2 ~ 5 배 적고 서버 쪽 지연은 그대로다.
  • 자동 묶기(r11496) : tick 을 실행기에서 돌리면 send_defer::auto_scope 가 소켓별 scope 와 같은 효과를 코드 수정 없이 낸다. 102만/s 에서 서버 CPU 가 r11478 대비 1/3 ~ 1/18, 410만/s 요청을 전부 전달(0.11 ~ 0.12 µs/msg). echo 는 변화 없음.

측정 구성

  • 장비 : Linux 32 코어 서버 A(Ubuntu 26.04, kernel 7.0, g++ 15.2 -O3 -DNDEBUG). 서버 8 thread 를 논리 CPU 0-7, 클라이언트 8 thread 를 16-31 에 고정. 0-7 은 물리 코어 4개다.
  • 소스 : r11340 · r11461 · r11478 을 각각 svn export 해 따로 빌드했다. g = net::socket::tcp<>, b = tcp_buffered<>. cork 끔 / 켬은 같은 바이너리에서 net::io::send_cork::enable() 만 바꿨다.
  • 클라이언트 : CGDK 와 무관한 plain epoll 프로그램(echo 는 연결마다 depth 개를 띄워 두고 echo 가 오면 하나 더 보냄, push 는 받기만 함). 지연은 메시지에 찍힌 CLOCK_MONOTONIC 기준.
  • 반복과 간섭 거르기 : 구성을 번갈아 돌리고 셀마다 깨끗한 3회의 중앙값을 쓴다. 깨끗한 회차 = 결과가 나왔고, 서버가 일했고, 측정 중 다른 프로세스가 1 코어 미만. 아니면 같은 회차를 최대 6번 다시 돌린다. 시작 전에는 다른 벤치와 컴파일이 끝날 때까지 기다린다.
  • 서버 CPU/msg : 측정 구간의 서버 프로세스 CPU 시간 ÷ 받은 메시지 수.

tick push : 수신 handler 밖의 송신

2026-10-23, r11461. tick 스레드 4 개가 1 ms 마다 담당 소켓에 64 B 메시지 K 개를 보낸다(메시지마다 버퍼 할당). cork 는 동작하지 않는다. scope 는 send_defer::scope 를 소켓 하나의 K 개 송신(소켓별) 또는 tick 전체에 건 것이다.

루프백 측정의 함정 : 받는 쪽 스레드가 잠들어 있으면 그 스레드를 깨우는 비용이 보내는 쪽(서버)의 send 에 잡힌다. 묶어 보내면 덩어리 사이에 클라이언트가 잠들어, 서버 CPU 가 2 ~ 5 배 비싸 보이고 p50 에 깨어나는 시간(+29 ~ 40 µs)이 들어간다. 그래서 서버 자신의 비용과 지연은 클라이언트를 바쁜 대기(epoll_wait 타임아웃 0)로 돌려 따로 쟀다.

  • 송신 거부(send() false)는 측정 끝에 클라이언트가 연결을 끊는 구간에서만 났다. 서버를 먼저 멈추면 모든 구성에서 0 이다.
  • 그룹 브로드캐스트는 그룹 락이 send_defer 를 자동으로 걸어 해당 없다. 영향을 받는 것은 그룹 락 밖에서 한 소켓에 여러 메시지를 연달아 보내는 tick · 타이머 코드다.
// tick 스레드 : 소켓마다 그 소켓의 송신만 묶는다
for (auto& psocket : sockets)
{
    send_defer::scope scope;          // 범위가 끝나면 이 소켓에 모은 것을 send/sendmsg 1회로
    for (auto& msg : pending_of(psocket))
        psocket->send(msg);
}

r11496 부터 실행기에서 실행되는 tick 은 이 scope 가 없어도 같은 방식으로 묶인다(아래). 위 코드는 실행기 밖 thread(std::thread)에서 보낼 때 필요하다.

tick push : 자동 묶기 (r11496)

2026-10-24, r11496(send_defer::auto_scope). 실행기가 executable 하나를 실행할 때마다 자동 범위를 열고, 그 안의 그룹 락 · send cork 밖 send 를 소켓별로 모은다. 다른 소켓으로 넘어가면 앞 소켓 것을, 범위가 끝나면 마지막 소켓 것을 보낸다. tick 을 system executor 에서 실행, 서버 8 thread, 바쁜 대기 클라이언트, 깨끗한 3회 중앙값. 칸은 서버 µs/msg.

  • 검증 : Linux epoll · io_uring 두 모드에서 단위 테스트 전부 통과(test_send_defer_auto.cpp 4 개 포함 : 소켓 섞어 보내기, tick 묶음, 1 개씩, 보내고 closesocket, 예외, 다른 thread 와 동시 송신 × gather / buffered × 자동 켬 / 끔).
