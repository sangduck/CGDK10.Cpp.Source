비동기 post_execute_query의 사용자 callback은 post하는 것이 기본이며 START_PARAMETER.post_response=false로 직접 처리할 수 있다. 동기 execute_query 완료는 직접 처리한다. 파싱·응답 매칭은 I/O에서 수행한다. Redis 자동 send_cork와 해당 옵션은 제거했고 send_defer는 독립적으로 유지한다.

auto batch = querier->execute_query({"get key:1", "get key:2"});

querier->post_execute_query({"get key:1", "get key:2"},
    [](CGDK::query::redis::querier::batch_results&& results) {

    });

// 동적으로 만든 명령도 같은 함수 이름을 쓴다.
std::vector<std::string> commands{"get key:1", "get key:2"};
auto result = querier->execute_query(commands); // 일반 문맥: 동기 실행
// CGDK coroutine 안: auto result = co_await querier->execute_query(commands);

execute_query()는 기존 단건 API와 같이 일반 문맥에서는 동기 실행하고 CGDK coroutine 안에서 co_await하면 비동기로 이어간다. 지연 실행은 명령 문자열을 소유하므로 원본 컨테이너가 사라져도 안전하다. post_execute_query()는 반환 전에 입력을 소유하고 세션에서 전송 직전에 묶어 인코딩한다.

배치의 각 원소는 명령 하나다. 입력 문법은 기존 API와 같은 공백·탭 구분 문자열이며, 바이너리 인자/따옴표 파서는 이번 변경에 포함하지 않았다. Pipeline은 Redis transaction이 아니다.

수정 내용과 처리 구조

  • 임시 문자열 무한 재귀 수정: post_execute_query(std::string&&, callback)가 자기 자신을 부르던 forwarding을 기존 문자열 처리 경로로 연결했다.
  • 배치 등록: 배치마다 세션 선택, query 객체, 요청 큐 노드, 명령용 RESP 버퍼를 각각 하나씩 사용한다. 모든 명령을 한 버퍼에 인코딩한 뒤 송신 API를 한 번 호출한다. 커널 부분 송신은 기존 송신 경로가 처리한다.
  • 응답 처리: 큐의 배치 노드는 필요한 응답을 모두 받을 때까지 유지한다. batch의 연속 응답은 최대256개씩 같은 큐 락에서 파싱·매칭하고 성공/실패 통계를 합산한다. 최종 완료 통지는 한 번 실행한다.
  • 동기 대기: 기존 shared 세션 할당 규칙(FIFO, 공유 대기의 100ms fallback)을 사용한다. scoped_thread_block으로 지연 송신을 비우고 중지하며, 요청 세대와 원자적 완료 상태의 wait/notify로 전체 배치 완료를 기다린다.
  • 결과 접근: const 결과에도 resp_data::operator[]를 사용할 수 있게 했다. 세션이 없는 coroutine 결과 query도 풀 반환 시 상태를 NONE으로 초기화한다.
단건 N회: N × [query 준비 → 세션 선택 → 큐 등록 → 완료 통지]
배치 1회: 명령 N개 인코딩 → query 1개 → 세션 1개 → 큐 노드 1개
          → 응답 N개 파싱·통계 → 전체 완료 통지 1회

send_cork/send_defer는 send() 경로의 송신을 모은다. 배치 구현은 그 앞의 query 생성·세션 선택·요청 등록 비용을 줄인다. 단건과 배치 모두 기존 송신 경로를 사용한다.

완료·오류·취소 계약

  • 빈 배치, 빈/공백뿐인 명령, 시작하지 않은 querier는 예외로 거부한다. 전체 명령을 인코딩한 뒤 등록하므로 잘못된 입력의 앞부분만 전송하지 않는다.
  • Redis 명령 오류는 해당 위치의 ERROR_로 보존하고 뒤 응답을 계속 수집한다. 결과 순서와 개수는 입력 순서와 개수에 대응한다.
  • 진행 중 stop/연결 단절은 이미 받은 결과를 유지하고 미수신 항목을 NONE_으로 남긴다. 동기 결과는 배열로, 비동기 결과는 한 번의 callback으로 전달한다. 동기 세션 할당 대기가 취소되거나 전송 자체가 실패하면 기존 동기 API처럼 예외가 발생할 수 있다.
  • NONE_은 응답을 못 받았다는 뜻이다. 서버에서 실행되지 않았다는 보장은 없으므로 끊긴 배치는 자동 재전송하지 않는다. 기존 단건 요청의 reconnect 정책은 유지한다.
  • 비동기 callback은 큐·querier 락 밖에서 실행하며 실패/취소 시 호출 스레드에서 바로 실행될 수도 있다. callback에서 다음 요청을 post할 수 있다.
  • 각 명령이 응답 하나를 만드는 pipeline용 API다. 응답 억제·Pub/Sub 전환 명령은 이 계약에 맞지 않는다. 전체 완료까지 결과를 보관하므로 큰 배치는 메모리를 더 사용한다.

제공 목적과 성능 개선 방향

coroutine은 비동기 요청을 순차적인 코드로 작성하고 결과·예외·객체 수명을 쉽게 다루기 위한 편의 API다. coroutine 평가는 사용 편의성, 정확성, 불필요한 오버헤드의 회귀 방지에 둔다.

  • 비동기 post_execute_query: 명령 인코딩·할당, 세션 선택, 큐/락, 완료 callback 비용을 줄인다.
  • 동기 execute_query: 응답 대기·깨움과 동기화, query 준비·재사용 비용을 줄여 단건 왕복시간을 개선한다.
  • 동기·비동기 batch: 명령별 준비·할당, 연속 버퍼 인코딩, 큐 등록, 송신과 응답 수집 비용을 개선한다.

성능 개선은 같은 조건의 변경 전후 처리량, p50/p99 응답시간, 명령당 CPU 시간으로 검증한다. batch는 전체 완료 지연시간도 함께 기록한다. 아래 coroutine 측정은 API 선택 비용을 이해하는 참고 자료로 보존한다.

원시 로그 · 전체 지표 요약

원시 로그에는 클라이언트별 처리량, p50/p99/p99.9, CPU µs/명령, Redis CPU와 오류 수가 있다. request 생성까지 지연시간에 포함하도록 Boost.Redis 측정 구간도 맞췄다. Redis와 제3자 라이브러리는 기존 설치를 재사용했고 벤치마크 실행 파일은 이번 소스로 다시 빌드했다. CGDK의 다른 의존 라이브러리는 기존 Claude 검증 환경을 재사용했으며 SDK HEAD 전체 재빌드 비교나 io_uring 모드별 비교는 아니다.

기본 executor에서 응답을 다시 전달하는 coroutine은 처리량이 자동으로 높아지지 않았다. Redis I/O executor에서 이어가면 p50 23.7 → 21.4 µs, 처리량 41,865 → 46,676/s로 개선됐다. 같은 호스트에서 Redis와 같은 L3의 CPU로 클라이언트를 옮긴 경우 이 경로는 61,026/s, p50 16.3 µs, p99 18.3 µs였다. callback은 69,081/s, hiredis는 74,586/s였다. 이 CPU 배치 효과를 원격 Redis 환경에 그대로 적용할 수는 없다.

executor 배치와 CPU/L3 배치에 따른 차이는 실행 환경을 이해하기 위한 참고 결과다. 전용 query 재사용은 이번 단건 실험에서 큰 차이를 만들지 않았고, TCP_NODELAY는 SDK 기본값이 이미 활성화되어 있다. 성능 구현 작업은 위의 비동기·동기·batch 경로를 우선한다.

execute_query_sync 공개 이름은 execute_query로 통합했다. 일반 호출은 동기 실행되고, CGDK coroutine에서 co_await하면 응답 완료 후 이어진다. 내부 동기 helper는 protected로 제한했다. 위 183회 측정 후 이름을 통합했고 새 API로 라이브러리 재빌드, 실 Redis 기능 검증과 단건 비교 10회를 추가 확인했다.

auto single = querier->execute_query("get key:1");
auto batch = querier->execute_query({"get key:1", "get key:2"});
// CGDK coroutine 안에서:
auto response = co_await querier->execute_query("get key:1");

검증과 재실행

  • Windows v145 x64 Redis 라이브러리 Debug/Release: 컴파일 경고·오류 0. Windows Redis 테스트 11개, Linux server_query 테스트 27개 통과.
  • 실 Redis: 세션 1/4개에서 각 12,000건을 동기·비동기로 교차 검증. 응답 내용·순서, 오류, 단건/배치 타입 선택, 128KB 값, 전용 세션 대기와 입력 수명, 부분 stop, 연결 단절, callback 재진입, coroutine의 입력 수명과 동기 대기를 확인했다.
  • 변경된 REQUEST_QUERY와 새 API 헤더를 사용하는 Redis 라이브러리·소비 프로그램은 재빌드해야 한다. 테스트용 격리 프로젝트에서 발생하는 MSB8028은 공유 IntDir에 관한 빌드 경고이며 라이브러리 컴파일 경고와 구분한다.
