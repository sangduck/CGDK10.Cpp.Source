Linux io 백엔드 비교 epoll · io_uring readiness · io_uring completion · epoll 혼합 등록 (2026-10-24 ~ 25)

epoll · io_uring readiness(POLL_ADD 로 epoll 흉내) · io_uring completion(worker 마다 ring, RECV · SEND op) 비교. 결과로 기본 백엔드를 completion 으로 변경(r11556). 커널이 막으면 epoll. epoll 은 ONESHOT 혼합 등록 적용(7절).

요약
  • 작은 메시지 : completion 이 모든 thread 수에서 1위, thread 와 같이 증가. 16 thread epoll 대비 tcp 64 B × 2.2, uds × 2.9, 16 B × 256 × 3.0. 메시지당 CPU 최소.
  • epoll : 8 thread 정점, 16 thread 부터 하락. 이벤트마다 epoll_ctl(MOD)(ONESHOT 재무장)가 공유 epoll 에서 경합. UDP 는 thread 증가에 따라 하락(window 32 : 68만 → 36만).
  • 64 KB : 접속 4개 · 4 thread 만 epoll 1위(32.1만 vs 20.9만). 8 thread 이상 · 접속 100 / 1000 은 completion 1위(최대 × 4.3).
  • readiness : TCP 작은 메시지에서 epoll 의 절반. 쓸 이유 없음.
  • epoll ONESHOT 제거 실험 : 동시 처리 오류 없음, 작은 메시지 +47 ~ +97%(16 · 32 thread), 64 KB 는 헛깨움 56 ~ 74%. 큰 수신 중에만 ONESHOT 인 혼합안으로 둘 다 해결 → 적용(7절).

측정 구성

  • 장비 A : POKPUNG, 32 CPU, kernel 7.0.0-38, g++ 15.2. 장비 B : SAKPUNG, 32 CPU, kernel 6.12(CentOS Stream 10, io_uring 꺼짐 → epoll 만). 둘 다 Release, loopback.
  • 벤치 : unit_test.net_socket.http/bench_linux_io.cpp 의 bench.epoll / bench.io_uring / bench.io_uring_completion. 서버 · 클라이언트가 한 프로세스, 같은 백엔드 · thread 수. 실제 net::socket::tcp<> · send() 사용. 케이스당 3초.
  • 값 : 받은 메시지/초 중앙값, 판 · 백엔드 순서를 돌린 교대 5라운드. 괄호 = 5회 범위. µs/msg = 프로세스 CPU ÷ 메시지(상대 비교용).

3. epoll 의 EPOLLONESHOT 제거 실험 (장비 B, r11540 : fd 고갈 수정 직후 HEAD)

ONESHOT 도입 이유 : 한 socket 에 여러 thread 동시 깨움 → 오류 · 비효율. 지금 코드에서도 생기는지 EPOLLET 만 쓰는 실험판(B)으로 확인.

  • 오류 없음 : 전체 스위트 Release 2회 · Debug 1회, 벤치 104회. 처리 중 이벤트는 상태 플래그(m_epoll_event_processing_now / m_epoll_event_flag_queued)만 쌓고 반환 → 동시 처리 없음. 같은 종류의 오류는 이 장치가 없는 UDP 경로에서 발생(r11537 : 스택 넘침, r11538 : EPOLLOUT 유실).
  • 헛깨움(처리 중 socket 에 온 이벤트) : 작은 메시지 0.01% 이하, 64 KB 는 8 thread 56% · 16 thread 74%. 세그먼트마다 edge → 쉬던 thread 깨움. ONESHOT 만 빼고 level 이면 97%.

6. 기본 백엔드와 확인 방법

  • 기본 백엔드 = io_uring completion(r11556 : 기본값 변경). 불가 시 epoll : kernel 6.0 전, kernel.io_uring_disabled(RHEL · CentOS 기본 2), docker 기본 seccomp.
  • 선택 : CGDK_IO_URING=epoll(0 / false / off) · 1(readiness) · completion, 또는 실행기 생성 전 executor::set_default_io_backend().
  • 시작 로그(r11557 : 백엔드 로그 추가) : 첫 io_context 생성 · 백엔드 변경 때 info 한 줄. 
    (info) io_context: io_uring enabled - backend 'io_uring completion' (asked, kernel 7.0.0-38-generic)
(info) io_context: io_uring disabled - backend 'epoll' instead of 'io_uring completion' (not available : kernel 6.12.0-273.el10.x86_64, kernel.io_uring_disabled 2, a seccomp profile (docker) may block it. io_uring completion needs 6.0+)
  • RHEL 계열 : /etc/sysctl.d/ 에 kernel.io_uring_disabled = 0(또는 1 + kernel.io_uring_group = <GID>) → sysctl --system. 호스트 값이라 컨테이너도 따름.
  • docker : io_uring_setup / io_uring_enter / io_uring_register 허용 seccomp 프로필(--security-opt seccomp=<json>). k8s : 그 프로필을 노드에 두고 Pod securityContext.seccompProfile = Localhost.
