send 최적화 net.io.sendable.*, net.io.Isendable.h, system/object/send_defer.h, net.definitions.socket.h

송신 경로에 들어간 최적화 기법을 플랫폼과 단계별로 정리한다. 목표는 세 가지다.

  • 메시지 수가 많아도 syscall 수를 늘리지 않는다(모아 보내기).
  • 보내는 쪽 thread 를 기다리게 하지 않는다(비동기, 락 최소화).
  • 느린 수신자 하나가 서버 메모리를 다 쓰지 않게 한다(큐 한도).

sendable 종류

socket 템플릿의 sendable 인자로 고른다. 기본은 Ntcp_async_gather 다.

클래스방식맞는 용도
Ntcp_sync, Ntcp_sync_buffered호출 thread 가 바로 보낸다. 큐·상태 관리 없음가끔 조금씩 보내는 소켓
Ntcp_async버퍼 하나씩 비동기 송신단순한 비동기
Ntcp_async_gather (기본)보내는 중이면 큐에 쌓고, 완료 때 큐 전체를 한 번에 보낸다일반 서버. 메시지가 많을수록 유리
Ntcp_async_gather_bufferedgather + 작은 메시지를 연속 버퍼에 복사해 합친다아주 작은 메시지를 대량으로 보낼 때
Nudp데이터그램. Linux 는 sendmmsg 배치UDP

Windows 에는 RIO(Registered I/O) 판(*.rio.cpp)과 raw 판(*_raw)도 있다.

모아 보내기 (gather)

보내는 thread 모델 (Ntcp_async_gather, 모든 플랫폼)

  • 소켓마다 "보내는 thread" 가 하나뿐이다(m_flag_sending).
  • 아무도 보내지 않으면 send 를 부른 thread 가 바로 보낸다. 큐를 거치지 않는다.
  • 누가 보내는 중이면 큐(m_queue_pending)에 넣고 바로 돌아간다. 호출자는 기다리지 않는다.
  • 보내는 thread 는 끝나면 그 사이 쌓인 큐 전체를 가져와(m_queue_pending ↔ m_queue_sending swap) 한 번에 보낸다. 큐가 빌 때까지 반복한 뒤 내려놓는다.
  • 두 큐는 std::vector 를 swap 하므로 용량이 재사용된다. 송신마다 할당하지 않는다.

한 번의 syscall 로 여러 버퍼

  • Windows : 큐의 버퍼를 WSABUF 배열로 WSASend 1회. 소켓당 진행 중인 WSASend 는 하나다.
  • Linux : iovec 배열로 sendmsg 1회(최대 IOV_MAX, 보통 1024). MSG_DONTWAIT.
  • 연속 메모리 합치기 : 새 버퍼가 바로 앞 버퍼에 이어진 메모리이고 owner 가 같으면 항목을 늘리기만 한다(QUEUE_SEND::push_back). 한 메모리 블록에 직렬화한 메시지들이 iovec 하나가 된다.

작은 메시지 복사 합치기 (Ntcp_async_gather_buffered)

  • BYTES_SEND_GATHER_BUFFER_MIN(1 KB)보다 작은 메시지는 연속 gather 버퍼에 복사한다. 버퍼는 1 KB 부터 BYTES_SEND_GATHER_BUFFER_MAX(64 KB)까지 자란다.
  • 큰 메시지는 복사하지 않고 버퍼째 붙인다.
  • 수천 개의 8 B 메시지가 iovec 몇 개로 줄어든다. 복사 비용과 iovec 처리 비용을 맞바꾼다.

송신 지연 (send_defer · send_cork)

여러 send 를 잠시 모았다가 한 번에 보내 syscall 과 패킷 수를 줄인다.

  • 그룹 락 안의 send (send_defer, r11352) : 그룹·멤버 락(group_lock_object) 안에서 보낸 send 는 thread_local 목록에 쌓이고, 가장 바깥 락이 풀릴 때 순서대로 flush 된다. 브로드캐스트처럼 락 안에서 많은 소켓에 보내는 코드가 락을 짧게 잡는다.
  • 수신 처리 중의 send (send_cork, epoll) : 받은 메시지들을 처리하면서 같은 소켓에 보내는 응답을 모았다가 처리가 끝나면 한 번의 sendmsg 로 보낸다. recv 한 번마다 flush 하므로 응답이 다음 recv 를 기다리지 않는다. 측정은 send cork · 서버 push.
  • 실행기 handler 의 send (send_defer::auto_scope, Linux, r11496) : 실행기(io_context 실행기, epoll · io_uring 의 post 실행)가 executable 하나를 실행할 때마다 자동 범위를 연다. 그 안에서 그룹 락 · send cork 밖의 send 는 소켓별로 모인다. 다른 소켓으로 넘어가면 앞 소켓 것을, 범위가 끝나면 마지막 소켓 것을 보낸다. tick · 타이머처럼 한 소켓에 여러 메시지를 연달아 보내는 코드가 코드 수정 없이 소켓별 send/sendmsg 1회가 된다. 끄려면 send_defer::enable_auto(false). 실행기 밖 thread(std::thread)는 자동으로 묶지 않으므로 send_defer::scope 를 직접 연다. Windows 는 자동 범위를 열지 않는다.
  • 조기 flush : 1024 개, 64 KB, 큐 한도의 절반 중 하나를 넘으면 범위가 끝나기 전에 보낸다. send cork 는 가장 오래 모은 send 가 200 µs(SEND_CORK_DURATION)를 넘어도 다음 send 때 보낸다. 그 나이는 send 마다가 아니라 송신 속도에 맞춰 1 ~ 32 send 마다 읽는다(r11471, 큰 묶음 push 처리량).
  • 순서 : 모으는 동안 다른 thread 가 보낸 것은 그 뒤에 쌓여 순서가 지켜진다.
  • close : 소켓을 닫기 전에 어느 thread 가 모은 것이든 먼저 보낸다(process_flush_deferred_send_on_close).
  • 교착 방지 : scoped_thread_block 은 들어갈 때 flush 하고 지연을 멈춘다. 락 안에서 동기 쿼리 응답을 기다려도 멈추지 않는다. 반대로 요청을 보낸 뒤 scoped_thread_block 없이 응답을 기다리면 요청이 아직 모여 있어 교착될 수 있다. r11496 부터 이 조건은 그룹 락 안만이 아니라 모든 실행기 handler 에 해당한다. 그런 곳은 기다리기 전에 send_defer::flush() 를 부르거나 enable_auto(false) 로 끈다.
  • Ntcp_async_gather(_buffered) 와 Nudp 가 지연을 구현한다. Windows 에서 WSASend 진행 중인 소켓은 지연 대신 pending 큐로 간다.

송신 큐 한도

  • 메시지 수 maximum_depth_of_send_buffer() 4096, 바이트 maximum_depth_of_send_buffer_bytes() 8 MB(accept 된 소켓 4 MB).
  • 넘으면 process_on_send_overflow 로 실패 처리한다. 느린 수신자 하나가 서버 메모리를 다 쓰지 않는다.
  • 보내는 thread 가 이미 가져간 묶음(Windows 의 진행 중 WSASend, Linux 의 EPOLLOUT 대기 잔량)은 한도에 세지 않는다(r11361). 두 플랫폼이 같은 규칙이다.
  • 큰 묶음을 한 번에 보내는 패턴에서 한도가 먼저 걸리지 않게 하려는 결정이다. 소켓은 "보내는 중인 묶음 + 한도" 만큼 담는다.

Windows (IOCP)

  • Overlapped WSASend + gather. 완료 통지가 다음 묶음을 이어 보낸다.
  • 송신 버퍼 SO_SNDBUF 를 명시 설정한다(최대 8 MB). 커널이 사용자 버퍼를 덜 기다리게 한다.
  • loopback 접속에 SIO_LOOPBACK_FAST_PATH 를 건다(acceptor listen 소켓, connect 소켓). 같은 host TCP 의 지연을 줄인다.
  • 핸들은 송신 락 안에서 읽고 send 까지 락 안에서 한다. close 가 같은 락 안에서 핸들을 무효로 바꾸므로, 닫힌 뒤 같은 값으로 재사용된 남의 소켓에 보내지 않는다.

Linux (epoll)

  • Proactor 처럼 쓴다. 호출 thread 가 바로 sendmsg 하고, 다 보냈으면 큐를 이어서 보낸다. EPOLLOUT 은 소켓 송신 버퍼가 찼을 때(EAGAIN, 부분 송신)만 건다.
  • 남은 바이트는 큐 앞에 되돌리고 EPOLLOUT 이 오면 process_recover_sendable 이 이어 보낸다.
  • 소켓 버퍼는 기본 미설정(커널 autotuning). net::io::socket::Ntcp::enable_explicit_socket_buffer_size(true) 면 명시 설정(r11393~).
  • SOCK_NONBLOCK 으로 생성·accept 해 접속당 fcntl 2회를 없앴다.
  • TCP socket option(r11394) : TCP_NODELAY(기본 on), TCP_NOTSENT_LOWAT(커널 송신 버퍼의 미전송 양을 제한해 지연을 줄임), TCP Fast Open(첫 send 가 SYN 에 실린다).
  • UDP : 다른 thread 의 송신·지연분·버퍼 가득 대기분을 sendmmsg 로 최대 64 개씩 보낸다. EWOULDBLOCK 이면 EPOLLOUT 을 기다려 이어 보낸다(이전엔 버림).

Linux (io_uring)

백엔드 구조와 벤치는 io_uring 백엔드 문서에 있다. 송신에 해당하는 것만 적는다.

  • MSG_ZEROCOPY : io_uring io_context 의 소켓만. 16 KB(zerocopy_threshold()) 이상의 단일 버퍼는 페이지를 고정해 복사 없이 보낸다. owner 는 커널 통지까지 붙든다. epoll 에서는 통지 처리 syscall 이 더 들어 손해라 쓰지 않는다. loopback 에서는 커널이 복사하므로 이득이 없다.
  • completion 모드(CGDK_IO_URING=completion) : 직접 send 는 그대로다(IOCP 의 WSASend 가 대개 그 자리에서 끝나는 것과 같다). 소켓 버퍼가 차면 EPOLLOUT 대신 남은 바이트로 SENDMSG op 를 내고, 그 완료가 이어서 보낸다. 큰 단일 버퍼는 SEND_ZC op(ENOBUFS 면 복사로 다시, r11490). Ntcp_async_gather 와 Ntcp_async_gather_buffered(r11494 부터) 모두. op 로 보내는 묶음은 송신 큐 한도에 세지 않는다.
  • CQE 배치 끝 송신(배치 send defer, r11497, 기본 on) : completion 실행기가 CQE 배치 하나를 send_defer 배치로 묶는다. multishot RECV 는 도착마다 CQE 를 내므로 CQE 마다 send cork 가 끝나 메시지당 send 0.76 회(epoll 0.15)였다 : 이제 배치 안 같은 소켓의 응답은 배치 끝에 한 번. cork 나이 상한(200 µs), 그룹 락 release flush, close 전 flush 는 배치 안에서도 그대로, 배치가 100 µs 를 넘으면 중간에 보낸다. 32 코어 tcp 64B x32 completion 11.0M → 18.0M msg/s(epoll 15.9M). CGDK_IO_URING_BATCH_DEFER=0 으로 끔.
  • ring 소유 worker 의 송신 op(r11457) : 그 소켓의 ring 을 가진 worker 는 send 대신 SENDMSG op 를 자기 ring 에 쓰고 다음 enter 로 제출한다(send syscall 없음). 창 16 패턴에서 -8%, 배치 send defer 와 같이 써도 손해라 기본 off(CGDK_IO_URING_SEND_OP=1 또는 enable_send_on_owner_ring(true)). 켜면 제출 전의 송신 op 를 같은 handler 의 graceful close 가 취소할 수 있다(알려진 문제).

UDS

  • 송신 코드는 TCP 와 같다. sendable 이 AF_UNIX 를 구분하지 않는다.
  • TCP socket option(TCP_NODELAY 등)과 MSG_ZEROCOPY 는 적용하지 않는다.
  • 같은 host 서버끼리 pipeline +26%, 64 KB +17%. 자세한 것은 UDS 문서.
